## Product direction

ENG-023 closes the Gate-3 semantic-density gap before ENG-030. An Agent can express “make this Stage locally playable” through one typed semantic capability and receive a deterministic repair plan, structured diagnostics, and normal GUIYI transaction evidence. The Tool does not create Editor-only automation, direct private-file mutation, a second Stage-validity truth, or a Talos-specific authoring route.

## Implementation boundary

Primary ownership remains the tactical-RPG toolkit, primarily `toolkits/tactical_rpg/tools`. No generic engine-core composite-command framework, new Tool kind, transaction-semantics change, Talos SDK/version/feature change, external dependency, Stage persistence schema change, or new workspace dependency edge was introduced.

`validate_stage` remains the only Stage-validity authority. ENG-023 defines its intent-local completion predicate as:

1. no `Error` diagnostics; and
2. no `STAGE_NO_SPAWN_POINT` warning.

No persisted playable flag or repair-plan truth exists.

## Delivered capability

### Live intent Command

`tactical.make_stage_playable(stage_id, spawn_object_id?, spawn_profile?)` is registered in the normal tactical Command registry and therefore appears in the combined live Tool catalog and existing ENG-014 Talos adapter without Talos-specific code.

The Tool:

- requires `EditContent`;
- declares access only to the target Stage;
- exposes machine-visible fallback defaults `spawn.player` and `player`;
- returns `stage_id`, `playable_before`, `playable_after`, ordered plan entries, `diagnostics_before`, and `diagnostics_after`;
- leaves `ToolResult.transaction` as the authoritative dry-run/applied transaction evidence.

The CLI command-schema golden intentionally grows from 17 to 18 Commands.

### Deterministic bounded repair plan

The plan is derived from authoritative Stage content and `validate_stage` diagnostics. Every authored action exposes an existing primitive Command ID, normalized machine-readable input, and reason code.

ENG-023 automatically repairs only:

- blocked existing spawn cells by delegating `stage.set_navigation_blocked(..., blocked=false)`; and
- missing spawns by delegating `stage.create_spawn` at the first deterministic valid unblocked grid coordinate in `q`-major then `r` order.

The complete candidate is preflighted on cloned engine state. If the bounded repairs cannot produce a locally playable Stage, the outer Command rejects atomically rather than committing a partial best-effort repair.

### Primitive semantic ownership and one outer transaction

The intent implementation reuses `SetNavigationBlockedCommand::apply` and `CreateSpawnCommand::apply` for authored changes. It does not hand-edit `StageDocument.navigation.blocked` or append a spawn through an alternate mutation path.

The intent itself remains one normal outer GUIYI Command transaction. Normal `CommandExecutor`/`AgentHost` schema normalization, permission, working-set, dry-run, diff, audit, persistence, and applied-only Project Graph refresh behavior is unchanged. No synthetic sub-transactions or second audit log are created.

### Structured blockers

Unsupported or ambiguous defects are not silently repaired. Tests preserve authoritative blockers such as `STAGE_OBJECT_OUT_OF_BOUNDS` and prove no partial mutation/audit record is committed. The implementation also leaves invalid dimensions, unsupported navigation state, arbitrary remaining unreachable topology, malformed tactical rules, cross-document reference/build failures, connection design, and delete/rename/game-specific choices outside automatic repair scope.

### Executable integration

The tactical demo now creates a Stage without a spawn, invokes `tactical.make_stage_playable`, verifies the returned `stage.create_spawn` plan, and then continues through existing actor/trigger/Encounter/Dialogue authoring, strict Stage+Encounter+Dialogue build, and Stage runtime load. This is direct executable integration evidence only; ENG-030 still owns the real Talos-driven create/repair/validate/build/preview production proof.

## Compatibility / migration

The change is additive: one new Tool ID and one new command-schema golden entry. Existing Stage document/artifact serialization, primitive Stage Tool IDs/schemas, Project Graph truth, build/preview semantics, and Talos integration remain unchanged. No content migration is required.

## Risks / limitations

“Locally playable” is intentionally Stage-local and narrower than whole-project buildability or game-design correctness. The bounded planner refuses repairs that require arbitrary design choices rather than hiding policy in automation. ENG-023 does not start a Talos session, invoke build/preview automatically, create Encounter/Dialogue content, or implement runtime movement/combat/world-state systems.

## Rollback

Remove the intent module/registration, focused tests, CLI golden entry/count change, tactical-demo intent call, and ENG-023 documentation. Existing Stage documents, primitive Stage Commands, navigation/reachability, Encounter, Dialogue/rule registry, Project Graph, build/runtime paths, and ENG-014 Talos adapter remain intact. Rollback must not replace the semantic intent with direct file mutation or Editor-private automation.

## ADR assessment

No new ADR was required. The implementation stays within accepted typed-command, transaction/dry-run, diagnostics, Project Graph, schema-validation, headless/Agent-first, and Talos-boundary decisions. No stop condition from Issue #69 was triggered.
