# ENG-012 validation — incremental Project Graph index

## Story

ENG-012 / GitHub Issue #54 maintains GUIYI's semantic Project Graph as a reusable incremental derived index instead of rebuilding or full-scanning relationships on every normal graph-backed Query.

Implementation PR: #55.

## Implemented boundary

- `DocumentEnvelope.references` remains authoritative semantic relationship data.
- `ProjectGraph` remains the serializable document adjacency/impact snapshot surface.
- `ProjectReference` normalizes one semantic edge for indexed lookup.
- `ProjectGraphIndex` maintains adjacency plus incoming/outgoing reference metadata.
- `QueryExecutor` owns the derived index and exposes rebuild, incremental refresh, invalidation, and snapshot APIs.
- `AgentHost::new` builds the graph once from the complete authoritative project state.
- successful `TransactionStatus::Applied` Commands refresh only IDs present in `TransactionReport.document_diffs`;
- previewed, rejected, and failed Commands do not refresh graph state;
- `AgentHost::replace_state` invalidates the graph for rollback/recovery;
- before any working-set filtering, `AgentHost` rebuilds an invalidated graph from the complete authoritative store, preventing a restricted caller from seeding a partial shared graph;
- Talos persistence rollback uses `replace_state` so derived graph state cannot survive an authoring-state rollback.

The graph is not persisted and does not introduce a second project truth.

## Machine-facing API changes

New public query-layer APIs:

- `ProjectReference`
- `ProjectGraphIndex`
- `ProjectGraph::dependencies`
- `ProjectGraph::dependents`
- `QueryHandler::execute_indexed` with a compatibility default
- `QueryExecutor::invalidate_project_graph`
- `QueryExecutor::rebuild_project_graph`
- `QueryExecutor::refresh_project_graph`
- `QueryExecutor::project_graph_snapshot`

`QueryExecutor::execute` now takes `&mut self` because the executor owns derived cache lifecycle. This is an alpha API compatibility change.

New `AgentHost` compatibility/recovery helpers:

- `replace_state`
- `invalidate_project_graph`
- `rebuild_project_graph`
- `project_graph_snapshot`

The existing Tool IDs and schemas for `project.references.find` and `project.impact.analyze` are unchanged.

## Acceptance scenarios

### A — reusable index

`guiyi-engine-query` unit coverage builds a `ProjectGraphIndex`, reuses the cached snapshot after the underlying store is changed directly, and observes the new relationship only after explicit incremental refresh. Normal `AgentHost` construction builds the graph once from authoritative state.

### B — incremental applied mutation

`crates/engine_agent_host/tests/project_graph_index.rs` initializes impact, applies a reference-retarget Command, and verifies the next impact Query reflects the applied transaction. The production hook refreshes only `report.document_diffs` IDs.

### C — dry-run and failure safety

The AgentHost integration test dry-runs the same mutation and verifies graph-backed Queries remain unchanged. Production refresh is gated on `TransactionStatus::Applied`; rejected/failed results never reach the refresh branch.

### D — working-set isolation

Unit and AgentHost integration tests create `doc.a <- doc.hidden <- doc.c`, then restrict the session to `doc.a` and `doc.c`. Impact on `doc.a` is empty: the query neither returns `doc.hidden` nor traverses through it to reveal `doc.c`. `project.references.find` likewise omits the hidden source.

A separate rollback regression replaces host state, makes the first subsequent graph Query through a restricted working set, and then verifies an unrestricted caller still observes the complete graph. This proves invalidation is rebuilt from the authoritative full store before filtering and cannot be poisoned by a partial security view.

### E — create/delete and dangling references

Query-layer tests refresh changed/deleted source Documents and preserve incoming references whose target Document has been deleted.

AgentHost integration coverage additionally executes the built-in `document.create` and `document.delete` Commands through the real transaction path. The created Document appears as a graph node after apply; deleting a target Document removes its own source node while retaining another Document's incoming reference to that now-missing target. Dangling semantic references therefore remain discoverable rather than silently disappearing with the target node.

### F — Talos/direct-client availability

The graph Queries remain live schema-bearing Tool catalog capabilities, so ENG-014's live-catalog Talos adapter exposes them without Talos-specific graph code. Direct clients can own `QueryExecutor` / `AgentHost` and use graph APIs without constructing Talos.

## Compatibility

- Project content and persistence formats do not change.
- Query Tool IDs and schemas do not change.
- direct calls to an individual `QueryHandler::execute` keep one-shot legacy behavior; normal executor/host calls use the index.
- `QueryExecutor::execute(&mut self, ...)` is the receiver-level alpha source compatibility change.
- the public alpha `AgentHost::state` field still exists. Callers that mutate it after host construction must call `invalidate_project_graph` or `rebuild_project_graph`; state replacement should use `replace_state`.

## Risks and limitations

- Index correctness depends on all normal authoring mutations continuing to flow through transaction-producing Commands or explicitly invalidating/rebuilding after out-of-band state mutation.
- ENG-012 indexes the existing `ContentReference` contract; it does not infer undeclared relationships from arbitrary payload fields.
- The graph is in-memory derived state. Persisted cache/performance policy remains future stabilization work.
- This Story does not implement a visual graph UI, graph database, or ENG-013 Stage commands.

## Rollback

Remove `ProjectGraphIndex`, indexed Query overrides, and AgentHost refresh/invalidation hooks. Restore `project.references.find` to visible-store scanning and `project.impact.analyze` to one-shot `ProjectGraph::build`. No project data migration or transaction rollback is required because Documents remain authoritative throughout.

## ADR assessment

No new long-term architectural decision is introduced beyond accepted ADR-0011. ENG-012 implements that existing semantic Project Graph decision as an incremental derived index. A new ADR is therefore not required for this Story.
