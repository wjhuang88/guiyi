# ENG-013 validation — semantic Stage object move/remove Commands

## Story

- Story: ENG-013
- GitHub Issue: #57

- Primary ownership: GUIYI tactical-RPG toolkit
- Base: ENG-012 merged main `eed94d8d7d6a63b73c103198af1c33564ffa6bfe`

## Product-direction contribution

ENG-013 advances GUIYI's Agent-first development surface. The Agent interaction layer is intended to perform normal project understanding, semantic authoring, validation, build, preview, and repair work that a traditional engine Editor would otherwise mediate. A visual Editor is a secondary client of the same Commands, Queries, diagnostics, transactions, and project models, not a second authoring truth.

For ENG-013 specifically, moving or removing an existing Stage object is no longer an editor-only gesture or a reason to use generic document-field mutation. It is a discoverable game-semantic capability.

This clarification strengthens existing AI-native/editor-as-client governance and does not change dependency ownership, so no new ADR is required.

## Implemented boundary

### `stage.move_object`

- Inputs: `stage_id`, `object_id`, `q`, `r`.
- Requires `EditContent`.
- Declares access to the target Stage document.
- Preserves stable object ID, kind, properties, and semantic references.
- Validates the candidate Stage with the existing tactical validator.
- Reuses `STAGE_OBJECT_OUT_OF_BOUNDS` for illegal coordinates.
- Returns normal GUIYI dry-run/applied transaction, diff, diagnostics, and audit evidence.

### `stage.remove_object`

- Inputs: `stage_id`, `object_id`.
- Requires `EditContent`.
- Declares access to the target Stage document.
- Removes the object by stable ID and validates the candidate Stage.
- Preserves non-blocking candidate diagnostics such as `STAGE_NO_SPAWN_POINT` in the transaction report.
- Regenerating the Stage envelope after Actor removal deletes that object's derived `actor_definition` reference; the normal ENG-012 transaction-diff refresh updates Project Graph query results.

### Structured missing-object failure

Both Commands return `STAGE_OBJECT_NOT_FOUND` as a structured validation diagnostic with Stage/object location and no authoritative mutation.

## Machine-facing API changes

New live Tool IDs:

- `stage.move_object`
- `stage.remove_object`

The Stage document schema and persistence format are unchanged. Existing Tool IDs and schemas are unchanged. The CLI command-schema golden grows from 8 to 10 commands so capability discovery treats the new semantic Commands as first-class public Tools.

No Talos-specific registration was added. The ENG-014 adapter continues to consume the live GUIYI catalog, so these capabilities become Talos `AgentTool`s automatically while Workbench/CLI/direct clients remain Talos-independent.

## Acceptance scenarios

### A. Move success

Integration coverage applies an in-bounds move and verifies:

- applied transaction status;
- one modified Stage document diff;
- stable object ID preserved;
- object kind/properties preserved;
- position updated.

### B. Move dry-run

Coverage dry-runs the same semantic move and verifies:

- previewed transaction status;
- reviewable Stage document diff;
- from/to output;
- authoritative Stage remains unchanged;
- preview audit record is present.

### C. Bounds rejection

An out-of-bounds candidate move returns `STAGE_OBJECT_OUT_OF_BOUNDS` with Stage ID, object ID, and position location. State and audit remain unchanged by the rejected validation path.

### D. Remove success and Project Graph refresh

Coverage removes Stage objects and verifies:

- applied Stage document diff;
- target object absent afterward;
- removing the last spawn returns `STAGE_NO_SPAWN_POINT` as a non-blocking transaction warning;
- removing an Actor through `AgentHost` removes its `actor_definition` result from `project.references.find` after the applied transaction.

### E. Missing object / atomicity

Both move and remove of an unknown stable object ID return exactly `STAGE_OBJECT_NOT_FOUND` in the focused tests and leave authoritative state unchanged.

### F. Security and capability discovery

Coverage verifies:

- read-only AgentHost execution is rejected with `AGENT_PERMISSION_DENIED`;
- out-of-working-set mutation is rejected with `AGENT_WORKING_SET_DENIED`;
- host state remains unchanged on both rejections;
- both Commands advertise live schema-bearing descriptors;
- the CLI public command-schema fixture includes both new Commands.

## Compatibility / migration

- No Stage document schema migration.
- No project storage migration.
- No Talos dependency/version/feature change.
- Existing Commands/Queries remain unchanged.
- Two additive Tool IDs are introduced.
- Stable object IDs survive move and are removed only by explicit semantic removal.
- CLI/tool capability consumers must accept the catalog growing by the two new schema-bearing Commands.

## Risks / limitations

- ENG-013 does not define occupancy/collision or tactical movement legality beyond existing Stage bounds validation.
- Removing a Stage object does not remove unrelated Stage connections; object and connection semantics remain separate.
- No batch or multi-object transaction-level intent Tool is introduced.
- The implementation uses the existing Stage validator as the candidate-state authority; future tactical constraints belong in the appropriate validator/toolkit Story rather than private command logic.

## Rollback

Remove the two command handlers/registrations, ENG-013 tests, and capability-golden entries. Stage documents and persistence formats require no migration. Do not replace rollback with a hidden editor-only mutation path or Talos-specific mutation implementation.
