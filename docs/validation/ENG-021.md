## Story

- Story: ENG-021

## Product-direction contribution

ENG-021 advances GUIYI's Agent-first development surface by making tactical Encounter composition a typed machine-facing capability. Binding a Stage, choosing stable participants, actor definitions, spawn points, and sides is normal game-development authoring work and must not depend on a visual Editor-only table or raw document patching.

A future Encounter Editor may visualize participants, references, diagnostics, and transaction diffs, but it must invoke the same authoritative Commands and Queries. It does not own a second Encounter format, relationship graph, or mutation path.

No new ADR is required. ENG-021 applies the accepted typed-command, transaction, diagnostics, Project Graph, headless-first, toolkit-ownership, and Agent-first/editor-as-client decisions without changing dependency ownership.

## Implemented boundary

### Encounter authoring model

The tactical content crate now defines:

- `EncounterDocument { id, name, stage, participants }`;
- `EncounterParticipant { id, actor_definition, spawn_point, side }`;
- document type `tactical.encounter.document`;
- artifact type `tactical.encounter.artifact`.

The Encounter owns tactical composition only. Stage geometry/navigation remains in Stage documents, actor definitions remain separate documents, and live combat state is not persisted into Encounter authoring content.

### Authoritative semantic references

`EncounterDocument::to_envelope` emits deterministic `DocumentEnvelope.references`:

- `encounter_stage`: Encounter -> Stage;
- `encounter_actor_definition`: participant -> actor-definition document;
- `encounter_spawn_point`: participant -> spawn object in the Encounter Stage.

`DocumentEnvelope.references` remains the source of truth. ENG-012 `ProjectGraphIndex` stays a derived cache and receives normal applied-transaction refreshes; ENG-021 adds no second Encounter graph.

### Deterministic Encounter compiler

`EncounterCompiler` compiles `tactical.encounter.document` into `tactical.encounter.artifact` through the standard `ArtifactEnvelope` source-hash/integrity path.

Local compile checks reject:

- an empty Encounter name;
- duplicate participant IDs;
- an empty participant side.

The artifact payload preserves the Encounter name, Stage ID, participant order, stable participant IDs, actor-definition IDs, spawn-point IDs, and sides. The compiler does not perform hidden project reads or own runtime combat behavior.

CLI and tactical-demo build paths register both `StageCompiler` and `EncounterCompiler`. Actor-definition documents are explicitly marked authoring-only for this slice rather than inventing a fake runtime compiler.

### Shared Encounter validation

Local `validate_encounter` diagnostics:

- `ENCOUNTER_NAME_EMPTY` — error;
- `ENCOUNTER_NO_PARTICIPANTS` — non-blocking warning for incremental authoring;
- `ENCOUNTER_DUPLICATE_PARTICIPANT_ID` — error;
- `ENCOUNTER_PARTICIPANT_SIDE_EMPTY` — error.

Project-aware `validate_encounter_project` additionally reports:

- `ENCOUNTER_STAGE_NOT_FOUND`;
- `ENCOUNTER_STAGE_INVALID_TYPE`;
- `ENCOUNTER_SPAWN_NOT_FOUND`;
- `ENCOUNTER_SPAWN_INVALID_KIND`.

Generic unresolved document references remain owned by the existing strict project/build reference gates; Encounter validation does not duplicate the engine-wide reference system.

### `encounter.create`

Inputs: `encounter_id`, `name`, `stage_id`.

The Command:

- requires `EditContent`;
- declares Encounter and Stage access;
- rejects duplicate document IDs atomically;
- project-validates the candidate;
- permits an initial zero-participant Encounter while returning `ENCOUNTER_NO_PARTICIPANTS` in the transaction report;
- uses normal dry-run, diff, audit, transaction, persistence, permission, and working-set boundaries.

### `encounter.add_participant`

Inputs: `encounter_id`, `stage_id`, `participant_id`, `actor_definition`, `spawn_point`, `side`.

The Command:

- requires `EditContent`;
- declares Encounter, Stage, and actor-definition document access before execution;
- requires supplied `stage_id` to match persisted Encounter Stage (`ENCOUNTER_STAGE_MISMATCH` otherwise);
- preserves stable participant identity;
- validates participant structure and referenced Stage spawn semantics before commit;
- rejects duplicate participant IDs, missing spawn objects, invalid spawn kinds, and other blocking diagnostics atomically;
- regenerates authoritative Encounter references on apply.

### `encounter.remove_participant`

Inputs: `encounter_id`, `participant_id`.

The Command removes by stable participant ID. An unknown ID returns `ENCOUNTER_PARTICIPANT_NOT_FOUND` without mutation. Removing the final participant is legal and returns `ENCOUNTER_NO_PARTICIPANTS` as a non-blocking warning.

### Existing read-side APIs remain canonical

ENG-021 does not add a redundant Encounter-only Query model. Built-in document Queries inspect Encounter content and Project Graph Queries inspect semantic relationships. This keeps one machine-facing read authority and avoids mirroring the same state in a second API surface.

## Machine-facing API changes

New live Command Tool IDs:

- `encounter.create`;
- `encounter.add_participant`;
- `encounter.remove_participant`.

The CLI command-schema golden intentionally grows from 11 to 14 Commands. All three new Commands advertise machine-readable schemas through the normal tactical registry and combined Tool catalog. The ENG-014 Talos adapter consumes the live catalog automatically; no Talos-specific Encounter registration was added.

Direct Workbench/CLI/AgentHost/toolkit clients remain Talos-independent.

## Acceptance evidence

### A. Content/reference model

Content tests prove an Encounter round-trips through `DocumentEnvelope` and emits deterministic Stage, actor-definition, and spawn-object references with stable participant source IDs.

### B. Compiler integrity

Content tests prove `EncounterCompiler` preserves stable participant order/identity and produces a normal artifact whose `source_hash` matches the source document and whose `artifact_hash` matches recomputed integrity. Invalid local authoring content is rejected deterministically.

### C. Project-aware diagnostics

Validation tests prove:

- empty name and no-participant warning behavior;
- duplicate participant and empty side diagnostics;
- valid Stage/spawn semantics pass;
- missing spawn returns `ENCOUNTER_SPAWN_NOT_FOUND`;
- a non-SpawnPoint target returns `ENCOUNTER_SPAWN_INVALID_KIND`;
- missing/wrong Stage documents return structured Stage diagnostics.

### D. Strict build integration

CLI integration tests register Stage and Encounter compilers with actor definitions marked authoring-only. A valid actor-definition + Stage + Encounter store produces exactly the Stage and Encounter artifacts. Removing the actor-definition document reuses the generic `BUILD_UNRESOLVED_REFERENCE` gate and produces no partial artifacts.

The tactical demo creates an actor definition, Stage, spawn, placed actor, Encounter, and participant through normal semantic Commands; its build produces Stage + Encounter artifacts while keeping the actor definition authoring-only, then runtime-loads the Stage artifact normally.

### E. Command transaction behavior

Tool integration coverage proves:

- `encounter.create` dry-run returns a preview diff without authoritative mutation;
- create apply commits normally and preserves `ENCOUNTER_NO_PARTICIPANTS` warning evidence;
- participant add produces one Encounter diff and regenerated semantic references;
- duplicate participant, missing spawn, and Stage mismatch fail atomically;
- final-participant removal applies and returns the no-participants warning;
- missing participant removal fails atomically with `ENCOUNTER_PARTICIPANT_NOT_FOUND`;
- successful/previewed paths retain normal audit evidence.

### F. AgentHost security and Project Graph refresh

AgentHost coverage proves:

- a read-only caller cannot add an Encounter participant;
- a content author whose working set includes Encounter + actor definition but excludes the Stage is rejected with `AGENT_WORKING_SET_DENIED`, proving the complete declared read set is enforced;
- authoritative state remains unchanged on permission/working-set rejection;
- adding a participant through AgentHost makes `project.references.find` observe the new actor-definition relationship through the normal ENG-012 applied-transaction graph refresh;
- removing the participant removes that graph result through the same normal refresh path;
- all three Encounter Commands are present in the live Tool catalog with machine-readable required fields.

## Compatibility / migration

- Existing Stage documents and Tool IDs/schemas remain unchanged.
- Encounter document/artifact types are additive.
- Existing projects without Encounter content require no migration.
- New Tool IDs are additive only: `encounter.create`, `encounter.add_participant`, `encounter.remove_participant`.
- CLI command capability count grows from 11 to 14.
- `DocumentEnvelope.references` remains the authoritative relationship truth; Project Graph remains derived.
- Actor definitions are authoring-only in this slice; no fake runtime compiler is introduced.
- No Talos dependency/version/feature change.
- No new external dependency or new workspace dependency edge is introduced.
- Reusable engine crates do not depend on tactical toolkit code.

## Risks / limitations

- Encounter composition does not define runtime initiative, turn scheduling, combat resolution, AI tactics, damage, victory/defeat evaluation, rewards, or combat-state persistence.
- `side` is currently a non-empty stable authoring string; faction semantics are intentionally not introduced in ENG-021.
- Spawn validation proves existence and SpawnPoint kind in the bound Stage, not game-specific occupancy or tactical legality.
- Actor definitions remain authoring-only for strict build purposes until a separately authorized runtime representation is required.
- Built-in document/Project Graph Queries are intentionally reused instead of introducing an Encounter-specific read projection.

These limits are intentional Story boundaries, not hidden runtime assumptions.

## Rollback

Remove the Encounter content/compiler/validation modules, the three additive Commands and registry entries, CLI/example compiler-validation wiring, ENG-021 tests, command-schema golden entries, and ENG-021 documentation.

Existing projects without Encounter documents require no migration. Projects authored with Encounter documents would lose that additive content under rollback, so rollback must be explicit rather than replacing it with an Editor-private Encounter format.
