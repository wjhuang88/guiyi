## Implemented boundary

- Added `integrations/talos_runtime` as GUIYI's thin outer Talos integration crate.
- Added crates.io `talos-runtime = =0.10.1` with `default-features = false` and no optional Talos features enabled.
- `talos-runtime` is the only direct Talos dependency in GUIYI; no direct `talos-agent`, `talos-core`, `talos-session`, `talos-permission`, or other Talos implementation-crate dependency was introduced.
- `GuiyiTalosAdapter` materializes individual Talos `AgentTool`s from the live GUIYI `ToolCatalog`, preserving Tool IDs, descriptions, and machine-readable input schemas.
- Every adapted Tool delegates to the existing `AgentHost::execute` authoritative execution path.
- Applied mutations persist through existing `ProjectStorage` / `ProjectTransaction`; dry-runs do not create storage commits.
- Talos permission/approval remains additive. GUIYI permissions, working sets, project scope, access planning, command validation, transactions, diagnostics, audit, and persistence remain independently authoritative.
- GUIYI `Rejected` / `Failed` Tool results are serialized as structured Talos Tool errors rather than runtime-fatal errors, allowing later legal Tool calls to continue.
- Direct JSONL Workbench, CLI, examples, and tests remain usable without starting Talos.

## Talos SDK contract

Version: `0.10.1`

Source: crates.io through the committed `Cargo.lock`.

Features: `default-features = false`; no optional Talos features enabled.

Direct Talos dependencies: `talos-runtime` only.

Public SDK surface used includes `RuntimeBuilder`, `AgentTool`, `RuntimeHandle` behavior, `LanguageModel`, Tool result types, permission rules, and typed session/Agent events re-exported by `talos-runtime`.

ENG-014 re-verified the approved 0.10.1 release line before implementation and did not silently upgrade the pre-1.0 dependency.

## Machine-facing API changes

New public integration types:

- `GuiyiExecutionContext`: GUIYI-owned session identity, domain permissions, and working-set scope exposed to the Talos adapter.
- `GuiyiTalosAdapter`: adapts the live GUIYI Tool catalog and registers individual Tools into a Talos `RuntimeBuilder`.
- `ProjectStoragePersistence`: outer persistence coordinator that commits successful applied GUIYI Commands through the existing crash-safe project-storage boundary.

Existing reusable GUIYI command/query/content/validation/build/runtime/toolkit crates remain Talos-independent.

## Agent lifecycle migration

- Talos is the canonical first-party Agent/session/turn lifecycle owner.
- `AgentHost::execute` remains the reusable GUIYI domain-execution seam.
- `AgentLoopDriver` and `AgentHost::run` are retained as compatibility-only alpha APIs with a documented sunset direction; the Talos path does not call them.
- `AgentSession` remains temporarily for direct clients and as an internal compatibility seam because `AgentHost::execute` still accepts it. Talos-facing code uses the narrower `GuiyiExecutionContext` instead.
- `AgentBudget` is classified as a legacy generic Agent action budget, not a distinct GUIYI domain-safety invariant. The Talos adapter sets the compatibility budget to an effectively non-limiting value so Talos owns first-party stopping policy.
- No provider/model abstraction, conversation runtime, planner, generic memory, retry, or stopping framework was added to GUIYI.

## Compatibility and migration

ENG-014 intentionally avoids a broad alpha API break. Direct clients keep the existing `AgentSession` / `AgentHost::execute` surface, while first-party Talos integration uses `GuiyiExecutionContext` and does not use GUIYI's generic loop driver.

Future removal of `AgentLoopDriver`, generic lifecycle fields, or legacy `AgentBudget` behavior requires a separately authorized migration with direct-client tests. No current client is forced to start Talos.

Talos is pre-1.0. Any future minor-version change from 0.10.1 is explicit compatibility work: re-check public facade/re-exports, feature requirements, typed events, permission behavior, Tool contracts, and lockfile resolution before upgrading.

## Risks and limitations

- The adapter still creates an internal legacy `AgentSession` because the current authoritative `AgentHost::execute` signature requires it; this is compatibility debt, not a second first-party lifecycle.
- Persistence coordination currently lives in the outer Talos integration crate. It intentionally reuses `ProjectStorage` / `ProjectTransaction` rather than creating a new transaction system.
- ENG-014 proves the runtime integration using deterministic scripted provider tests. The broader playable tactical-RPG product proof remains owned by later Stories such as ENG-030.
- Talos's own transitive dependency graph naturally includes its implementation crates; the GUIYI architecture rule concerns direct dependencies declared by GUIYI packages.

## Rollback

Before merge, rollback is removal of the ENG-014 branch/PR changes.

After merge, the integration can be disabled by removing `integrations/talos_runtime` from the workspace and the direct `talos-runtime` workspace dependency while preserving GUIYI's existing direct-client execution path. Do not remove or weaken GUIYI permission, working-set, transaction, audit, persistence, validation, or direct-client behavior as part of a Talos rollback.
