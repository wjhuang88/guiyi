# 完整迭代推进办法

## 1. 迭代长度

推荐每个迭代 1 周。

一个迭代只承诺：

- 1 个主目标
- 1–3 个主 Story
- 少量阻塞修复

不得把多个基础设施领域混进同一迭代。

## 2. 迭代节奏

### Day 0：准备

- 确认主目标。
- 检查依赖。
- 将 Story 置为 Ready。
- 建立 Iteration 文档。
- 记录基线验证结果。
- 预先定义 Demo。

### Day 1：边界和最小骨架

- 编写或批准 ADR。
- 建立接口。
- 建立测试夹具。
- 编写失败测试。
- 只完成最小纵向骨架。

### Day 2–3：核心实现

- 按验收标准逐项实现。
- 每完成一个验收点立即增加自动化测试。
- 每天结束执行局部门禁。
- 发现范围外问题进入 Backlog，不顺手扩展。

### Day 4：集成

- 接入 Preview 或样例项目。
- 执行跨 crate 测试。
- 执行错误路径。
- 执行重复生命周期测试。
- 同步 Reference。

### Day 5：验证与复盘

- 执行全部门禁。
- 演示用户路径。
- 输出验证报告。
- 记录遗留缺陷。
- 完成复盘。
- 更新 Roadmap 和 Backlog。

## 3. 每日状态格式

```text
完成：
- ENG-xxx 验收点 1

发现：
- 生命周期在第二次加载时泄漏 1 个实体

决定：
- 不在本迭代加入 Prefab 继承

下一步：
- 增加重复加载测试并修复
```

## 4. 主 Story 拆分原则

一个 Story 应能在 1–3 天内完成。

如果超过，应拆为：

```text
Iter A：接口和最小实现
Iter B：运行接入
Iter C：编辑器接入
Iter D：迁移和稳定化
```

## 5. 验证报告结构

- 基线
- 本次范围
- 自动化验证
- 手工验证
- 性能结果
- 内容迁移结果
- 已知缺陷
- 是否满足出口门禁
- 是否允许进入下一阶段

## 6. 失败处理

出现以下任一情况，迭代不得宣告完成：

- 自动化测试缺失
- 只能在开发者本机运行
- Reference 与代码冲突
- 必须绕过严格校验
- 使用临时硬编码才能 Demo
- 第二次运行结果不同
- 旧项目无法回滚

## 7. 一线开发执行顺序

```text
读取 Story
→ 阅读相关 ADR / Reference
→ 运行基线命令
→ 编写失败测试
→ 实现最小变更
→ 运行局部门禁
→ 集成 Preview / Sample
→ 更新文档
→ 执行全量门禁
→ 提交验证报告
→ PR
```
